# Правила работы с Codex

Документ нужен для работы с AI coding agents.

## Формат сотрудничества

- Неясные продуктовые решения сначала обсуждаются.
- Если пользователь спрашивает "почему" или "объясни", сначала нужно объяснить, а не молча менять направление.
- Если пользователь говорит "зафиксируй", "создай", "перенеси" или "реализуй", нужно сделать изменение и проверить результат.
- Сгенерированный код нужно ревьюить перед принятием.

## Инженерный стиль

- Следовать существующей структуре проекта, когда она появится.
- Держать изменения в рамках текущей задачи.
- Предпочитать понятный код преждевременным абстракциям.
- Не дублировать бизнес-логику.
- Идентификаторы в коде писать на английском.
- Комментарии и docstring можно писать на русском.
- Docstring нужны для модулей, классов, сервисных методов и неочевидной бизнес-логики.
- Не добавлять docstring в каждую тривиальную DTO или очевидную функцию только ради формальности.

## Архитектурный стиль

Backend строится слоями:

```text
API layer -> service layer -> repository/ORM layer
```

Дополнительные слои допустимы для schemas, validation, config, security, database, tests и shared utilities.

## Ревью

При ревью в первую очередь искать:

- баги и регрессии;
- проблемы безопасности;
- неверное поведение API;
- нехватку тестов;
- проблемы с проверкой владельца данных;
- дублирование бизнес-правил;
- названия, которые мешают будущим модулям.

## Субагенты

Субагенты используются как доступные роли, а не как обязательный pipeline для каждой задачи.

Базовые правила:

- инструкции для агентов в `AGENTS.md` и `.codex/agents/` можно писать на английском для стабильности модели;
- агент должен общаться с пользователем на русском;
- пользовательская документация, docstring и комментарии backend остаются на русском;
- по умолчанию работает один основной агент;
- обычная задача - максимум 1 субагент;
- сложная backend/auth/frontend задача - максимум 2 субагента;
- несколько пишущих агентов одновременно не запускать.

Роли лежат в `.codex/agents/`:

- `backend_worker` - backend-реализация маленькими патчами;
- `frontend_worker` - frontend-экраны и компоненты;
- `architecture_reviewer` - проверка слоев и структуры;
- `test_reviewer` - проверка тестов, fixtures, helpers и покрытия;
- `security_reviewer` - auth, cookies, CORS, secrets, permissions и user data access;
- `ui_reviewer` - визуальная проверка frontend по макетам;
- `pr_reviewer` - финальное read-only review перед PR;
- `docs_notion_helper` - список обновлений для docs/Notion.

Запускать нужно минимальный полезный набор, а не всех агентов подряд.
