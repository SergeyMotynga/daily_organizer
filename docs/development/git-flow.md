# Gitflow и доставка изменений

Этот документ задаёт правила Git для Daily Organizer. `AGENTS.md` и другие документы ссылаются на него. Явные указания пользователя для текущей задачи имеют приоритет.

## Выбор ветки

- `main` — стабильная production-ветка.
- `develop` — интеграционная ветка разработки.
- Обычная разработка, документация, тесты и рефакторинг идут в отдельных рабочих ветках от актуальной `origin/develop`, затем через PR в `develop`.
- `main` получает изменения из `develop` в рамках отдельно разрешённого выпуска. Прямые изменения в `main` и `develop` не выполняются.

| Префикс новой ветки | Когда использовать | База и целевая ветка |
|---|---|---|
| `feature/<description>` | Новая функциональность, документация, тесты, рефакторинг и технические задачи | Актуальная `develop` → `develop` |
| `bugfix/<description>` | Исправление ошибки в разработке | Актуальная `develop` → `develop` |
| `hotfix/<description>` | Срочная ошибка уже выпущенной production-версии | Маршрут согласуется в задаче исправления production |
| `release/<version>` | Подготовка явно заданного релиза | Маршрут согласуется в задаче выпуска |

Префиксы `hotfix/` и `release/` зарезервированы для соответствующих задач. Они сами по себе не меняют существующий порядок выпуска через `develop`; базу, цели PR и версию нужно определить до начала работы.

Описание ветки — короткое английское имя в kebab-case. Дополнительный префикс `codex/` не используется. Тип изменения документации или тестов отражается в коммите, а не отдельным префиксом ветки.

```text
feature/project-columns
feature/align-gitflow-docs
feature/task-regression-tests
bugfix/refresh-cookie
```

Перед изменениями агент:

1. Проверяет текущую ветку, рабочее дерево, индекс и remotes; сохраняет существующие изменения пользователя.
2. Продолжает опубликованную рабочую ветку, если задача относится к её открытому PR. После слияния или закрытия PR начинает новую задачу в новой ветке от актуальной `develop`; удалённую ветку завершённой задачи не публикует заново.
3. Для новой ветки обновляет remote-ссылки и проверяет имя через `git check-ref-format --branch <name>`. Если текущая ветка — `main` или `develop`, создаёт рабочую ветку перед редактированием. При несвязанных локальных изменениях может использовать отдельный worktree.
4. Определяет remote для push и цель PR до публикации. Если выбор действительно неоднозначен, уточняет его у пользователя.

## Коммиты

Используем Conventional Commits с английским заголовком:

```text
<type>(<optional-scope>): <English imperative description>
```

Один коммит соответствует одному логически связанному изменению. Обычный заголовок — до 72 символов. Для несовместимого изменения используется `!` и объяснение в body/footer.

```text
feat(projects): add column sorting
fix(auth): handle expired refresh sessions
docs: align gitflow and agent rules
test(tasks): cover date filters
refactor(tasks): split task service logic
```

Основные типы: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`, `build`, `style`, `ci`, `revert`.

Перед коммитом агент проверяет полный diff задачи, уже staged-файлы и `git diff --cached --check`. В коммит входят только изменения задачи; чужие правки в рабочем дереве и индексе сохраняются. Настроенные hooks выполняются без обхода.

## Проверки и PR

- Один PR закрывает одну понятную задачу или небольшой связанный набор изменений.
- До публикации выполняются относящиеся к задаче проверки из инструкций и конфигурации проекта, а также ревью diff. Изменения backend-логики, API, auth и правил задач требуют соответствующих тестов.
- Для обратимых изменений документации достаточно проверки diff, ссылок и согласованности правил. Приложение и его тесты ради таких правок запускать не требуется.
- Если обязательная проверка упала или недоступна, агент устраняет доступную причину, затем повторяет проверку. Незавершённую задачу публикует только по прямому запросу пользователя.
- Заголовок PR — Conventional Commit на английском; описание — на русском. Используются шаблон проекта, а при его отсутствии — личный шаблон пользователя: краткая суть, таблицы, небольшой бейдж типа и фактические статусы проверок.
- Новый PR создаётся черновиком. Если открытый PR рабочей ветки уже существует, агент обновляет его без дубликата и сохраняет его текущий draft/ready-статус.
- Успешные локальные проверки и открытый PR не означают успешный CI. Незапущенные проверки и неизвестный статус CI отмечаются явно.
- Перед слиянием в `develop` относящиеся к задаче форматирование, линтер и тесты должны проходить. Незавершённые эксперименты не попадают в `main`.

## Разрешения и завершение задачи

Пользователь заранее разрешил для завершённых задач, меняющих файлы репозитория, создавать коммиты, выполнять обычный push рабочей ветки и открывать либо обновлять черновой PR. Агент выполняет эти этапы по умолчанию после успешных проверок; повторное подтверждение не требуется, если текущий запрос не задаёт другой порядок.

Слияние PR, перевод draft в ready, force-push, переписывание чужой истории и удаление веток требуют отдельного прямого запроса пользователя. Запросы разрешений инструментов и ограничения среды остаются действующими; разрешение доставки не позволяет обходить их.

В личной среде пользователя перед выбором/созданием ветки, коммитом, push или работой с PR агент читает `C:/Users/motyn/.codex/workflows/git-delivery.md`, если файл доступен. Там определены детали валидации сообщения коммита и оформления PR; правила базовой и целевой веток проекта заданы выше. Репозиторий сохраняет самостоятельные правила для других сред.

На завершении агент сообщает результаты проверок, рабочую ветку, созданные коммиты и ссылку на PR. Если доставка заблокирована, указывает точную причину и уже выполненные этапы. Для консультации или ревью без изменения файлов публикация не требуется.
