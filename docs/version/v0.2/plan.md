# Daily Organizer v0.2: черновой план

`v0.2` начинается после функционального закрытия `v0.1`.

Главное правило: не превращать `v0.2` в бесконечный релиз. Лучше выбрать один продуктовый фокус и довести его до состояния "можно пользоваться".

## Возможные направления

### Вариант A. Notes / быстрые мысли

Изначальный roadmap предполагал, что `v0.2` добавит заметки и быстрые мысли.

Смысл:

- быстро записать мысль без превращения в задачу;
- хранить короткие заметки отдельно от todo;
- позже связывать заметки с задачами, проектами и AI/MCP.

Минимальный scope:

- CRUD заметок;
- список заметок;
- поиск;
- простые теги или без тегов на первом шаге;
- отдельный раздел в app shell;
- адаптивный UI в стиле v0.1.

### Вариант B. Product hardening

Если хочется сначала сделать `v0.1` надежнее перед новыми сущностями:

- визуальный QA pass;
- e2e-сценарии;
- accessibility-проверка;
- performance/code splitting;
- чистка frontend-компонентов после UI rebuild;
- стабилизация календаря и date filters.

### Вариант C. Deploy / infrastructure

Если цель - начать пользоваться приложением с разных устройств:

- Docker production build;
- CI checks;
- VPS;
- reverse proxy;
- HTTPS;
- домен;
- backup PostgreSQL;
- секреты и env configuration.

## Рекомендуемый следующий шаг

Сейчас лучше выбрать между:

1. `v0.2-notes` - новый продуктовый модуль.
2. `v0.2-hardening` - стабилизация и подготовка к deploy.
3. `v0.2-deploy` - инфраструктура для личного использования.

Для pet-проекта логичный путь:

```text
v0.2-hardening -> v0.2-deploy -> v0.3-notes
```

Но если хочется быстрее развивать продуктовую ценность:

```text
v0.2-notes -> hardening/deploy позже
```

## Что не стоит делать в v0.2

- Не добавлять AI/MCP раньше стабильных пользовательских сценариев.
- Не смешивать notes, deploy, finance и reports в одном PR.
- Не переписывать backend-архитектуру без конкретной боли.
- Не начинать нативное mobile app до стабильного web MVP.
